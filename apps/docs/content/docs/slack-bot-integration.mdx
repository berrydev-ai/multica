Multica uses your own Slack app. Once connected, team members can DM the Bot, @-mention it in a channel, or use `/issue` to create issues.

One Slack app maps to one Multica agent. To connect several agents, create a separate app for each.

## Before you start

The connection must be completed by a workspace owner or admin, and ends with two credentials pasted into Multica:

- a Bot User OAuth Token, starting with `xoxb-`;
- an App-level Token, starting with `xapp-`.

## 1. Create the Slack app from a manifest

Open [Slack API Apps](https://api.slack.com/apps), click **Create New App → From a manifest**, pick the Slack workspace, then paste the following under **YAML**:

```yaml
display_information:
  name: Multica
features:
  app_home:
    home_tab_enabled: false
    messages_tab_enabled: true
    messages_tab_read_only_enabled: false
  bot_user:
    display_name: Multica
    always_online: true
  slash_commands:
    - command: /issue
      description: Create a Multica issue
      usage_hint: "[description]"
oauth_config:
  scopes:
    bot:
      - app_mentions:read
      - channels:history
      - files:read
      - groups:history
      - im:history
      - mpim:history
      - chat:write
      - reactions:write
      - users:read
      - commands
settings:
  event_subscriptions:
    bot_events:
      - app_mention
      - message.im
      - message.channels
      - message.groups
      - message.mpim
  interactivity:
    is_enabled: false
  org_deploy_enabled: false
  socket_mode_enabled: true
  token_rotation_enabled: false
```

Before creating, you can replace both occurrences of `Multica` with the agent's name. Do not remove scopes or events from the manifest, or DMs, channel mentions, replies, or `/issue` may stop working.

<Callout type="warning">
If this Slack app was installed before attachment support was available, add the `files:read` Bot scope and reinstall the app to the workspace. Slack does not apply newly added scopes to the existing Bot token until the app is reinstalled.
</Callout>

The Bot connects out to Slack over Socket Mode, so no public Request URL or OAuth Redirect URL is needed.

## 2. Get the two tokens

### Bot token

1. In the Slack app, open **Install App**.
2. Click **Install to Workspace** and approve the permissions.
3. Copy the **Bot User OAuth Token** — it starts with `xoxb-`.


### App-level token

1. Open **Basic Information → App-Level Tokens**.
2. Click **Generate Token and Scopes**.
3. Add the `connections:write` scope.
4. Generate and copy the token starting with `xapp-`.


## 3. Connect it to an agent

1. In Multica, open **Agents** and select the agent to connect to Slack.
2. Go to **Integrations** and click **Connect Slack**.
3. Paste the Bot token and the App-level token.
4. Click **Connect**.

Multica verifies that the two tokens come from the same app. Once connected, the page shows **Connected to Slack**.

<Callout type="warning">
Both tokens are stored encrypted on the Multica server. Tokens are credentials — don't put them in issues, comments, or code repositories. An app already connected to another agent or workspace can't be reused directly; disconnect the original connection first.
</Callout>

## First use

The first time a member DMs or @-mentions the Bot, they receive an account binding link. Sign in with the Multica account for that workspace, then return to Slack and send the message again.

In a channel or group chat the link is sent privately — only the person who wrote the message sees it, and nothing appears in the conversation. Anyone who is not a member of the Multica workspace can request the link but cannot redeem it, and the Bot answers each person at most once a day.

The link is single-use and expires after 15 minutes. Once it expires, message the Bot again for a new one. Multiple Bots in the same Multica workspace can usually reuse an existing binding if they come from the same Slack workspace.

Only members of the current Multica workspace can use the Bot.

## Hand work to the agent in Slack

### Direct messages

Open the Bot from **Apps** in the Slack sidebar and message it directly — no @-mention needed.

### Channels and group chats

Run `/invite @your-bot` to add the Bot to the channel first, then send `@your-bot your request`. Each thread forms its own session; for follow-ups, keep @-mentioning the Bot in the original thread.

The Bot only responds to channel messages that explicitly @-mention it. When it runs, it reads the thread's recent context within the scopes its permissions allow.

### Send files

Attach files to a DM, or to a channel message that @-mentions the Bot. They arrive as attachments on the same piece of work, so the agent reads them together with your request.

This needs the `files:read` scope — if the app was installed before attachment support existed, see the note in step 1. Each file must be 20 MiB or smaller, and one message carries at most 10. Files that are larger, still uploading, or hosted outside Slack (a Google Drive or Dropbox link, for example) are skipped; the message text still reaches the agent.

### Create issues with `/issue`

In a channel or DM, type:

```text
/issue Safari stays on the login page after a successful sign-in
```

This command needs no @-mention. Multica hands the description to the agent behind the current Bot, which writes up the title and body and creates the issue. Slack first shows an acknowledgment visible only to you; when the issue is created, you get a notification in your Multica inbox.

## Restrict who and where the Bot serves

By default the Bot serves any conversation it has been invited to, once the sender has bound their account and is a member of the Multica workspace. That is enough for most teams: an outsider can talk to the Bot but gets no work out of it.

It is not enough when the Bot's answers are themselves sensitive. Everything the Bot says is visible to every person in the conversation, so a reply to an authorized member in a wide channel — or in a group chat that contains one guest — publishes that reply to all of them.

Set the installation's chat gate to `members_only` to authorize the conversation as well as the sender:

The two lists answer different questions and do not overlap. `auth_channel_id` decides **who** may use the Bot; `allowed_channel_ids` decides **where** it works. Holding the roster does not make that channel a place the Bot answers — list it in both if you want to talk to the Bot there too.

| Conversation | Served when |
| --- | --- |
| Direct message | The sender is bound and still a workspace member. |
| Group chat (multi-party DM) | Every non-bot participant is bound and still a workspace member. One outsider closes the conversation, even for an authorized sender. |
| Channel | The sender is authorized **and** the channel id appears in the installation's allowed channel list. |

A closed conversation costs a membership lookup and nothing else — no session, no agent run, no model usage. The sender is told privately that the Bot is unavailable there; nobody else sees anything.

Set it with:

```http
PUT /api/workspaces/{workspace_id}/slack/installations/{installation_id}/access
```

```json
{
  "chat_gate": "members_only",
  "auth_channel_id": "G0123456789",
  "refusal_text": "Not an authorized operator",
  "allowed_channel_ids": ["C0123456789"]
}
```

A person who is not on the roster is told so, privately, wherever they wrote — set `refusal_text` to say it in your own words, or leave it out for a deliberately uninformative default. Somebody who *is* on the roster but writes in a channel the Bot does not work in gets a different message naming the place instead, so they know to move rather than to ask for access.

Workspace owners and admins only. The body states the **complete** policy — omitting a field clears it rather than leaving the previous value — and the current policy comes back on every installation in `GET /slack/installations`.

Leave `allowed_channel_ids` out to reach the Bot in direct messages and authorized group chats only. Channel ids are case-sensitive.

### Use a Slack channel as the roster

Naming an `auth_channel_id` makes a private Slack channel's membership the authorization list. To grant access, invite the person to that channel; to revoke it, remove them. Nothing has to be edited or redeployed, and the list is visible in Slack to the people who maintain it.

The channel narrows the existing rule — it never widens it. A person must still have bound their Slack account and still be a member of the Multica workspace; the channel decides which of those members are in scope. Being in the channel does not make somebody a workspace member.

To find the id, open the channel in Slack, click its name, and copy the **Channel ID** at the bottom of the dialog.

Removals take effect within about 30 seconds. Invite the Bot to the channel before setting the policy — it cannot read a channel it is not in, and the request is rejected if it is not.

<Callout type="warning">
The channel must be **private**. Anyone can join a public channel, which would let anyone authorize themselves. Multica verifies this rather than trusting the setting: a public channel is rejected when the policy is saved, and re-checked on every roster refresh — so converting the channel to public later closes the Bot immediately instead of quietly widening who it serves.
</Callout>

Reading the channel needs the `groups:read` Bot scope. If Slack cannot be reached, the Bot keeps using the last known membership for up to 15 minutes so an outage does not silence it. A stale list can only keep serving people who were already on it — nobody new is admitted — so an outage delays a removal instead of granting access. After 15 minutes it stops guessing and closes. A channel that has turned public, or that the Bot has been removed from, is not an outage and gets no grace at all.

<Callout type="warning">
Authorizing a group chat reads its participant list, which needs the `mpim:read` Bot scope. Without it the list cannot be read, and a Bot set to `members_only` closes every group chat rather than guessing. Add the scope to the manifest and reinstall the app before relying on group chats.
</Callout>

## Manage connections

Open **Settings → Integrations** to view all connected Slack Bots. Workspace owners and admins can disconnect them.

After disconnecting, the Socket Mode connection stops and the Bot no longer receives new messages. Existing conversations and audit records are not deleted.

## Self-hosting setup

Multica Cloud needs no extra configuration. A self-hosted deployment must first set a key used to encrypt Slack tokens:

```dotenv
MULTICA_SLACK_SECRET_KEY=<base64-encoded 32-byte key>
```

Generate one like this:

```bash
openssl rand -base64 32
```

Restart the API server, then connect the Slack app. Keep this key long-term: if it is rotated or lost, existing tokens can no longer be decrypted and the Bot must be reconnected.

Account binding links use `MULTICA_APP_URL`, falling back to `FRONTEND_ORIGIN` when unset; it must point to a Multica address members can reach.

## Troubleshooting

- **Invalid token when connecting**: check the prefixes and confirm both tokens come from the same app.
- **App can't be verified**: confirm the manifest includes `users:read`, then reinstall the app after updating permissions.
- **No DM entry point**: confirm `app_home.messages_tab_enabled` is `true`.
- **No reply in a channel**: confirm the Bot has been invited to the channel and the message @-mentions it. If the installation uses `members_only`, also confirm the channel id is in its allowed channel list.
- **"Not available in this channel"**: the sender is authorized but the conversation is not — add the channel id to the installation's allowed channel list, or move the request to a DM.
- **A group chat stopped working**: under `members_only` every participant must be a bound workspace member, and the app needs `mpim:read`. Reinstall after adding the scope.
- **Everybody is refused after setting `auth_channel_id`**: confirm the Bot is still in that channel and the channel is still private. Both are re-checked continuously, and either one failing closes the Bot.
- **`/issue` doesn't exist**: confirm the manifest includes the slash command and the `commands` scope, then reinstall the app.
- **Files don't reach the agent**: confirm the manifest includes `files:read` and that the app was reinstalled after the scope was added, and check the file is 20 MiB or smaller.
- **The Bot doesn't run**: check whether the agent is archived and whether the [runtime](/daemon-runtimes) it uses is online.
